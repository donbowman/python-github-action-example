# python-github-action-example

A deliberately small Python service that demonstrates a complete, production-shaped
GitHub Actions pipeline:

- FastAPI with a JSON API
- SQLAlchemy 2.x ORM models
- Alembic migrations
- SQLite for the unit tests
- Poetry for dependency management, with a committed `poetry.lock`
- pytest, black and flake8
- pre-commit hooks, including a pre-push secret scan
- GitHub Actions for lint, test, filesystem scanning, image scanning and SBOMs
- Automatic semantic version bumps on every merge to `main`
- Container builds pushed to Azure Container Registry using GitHub OIDC, with no PAT

Python 3.14 only. No version matrix.

## Layout

```text
.
├── .github/workflows/       CI, Security, Release and Container workflows
├── docs/rulesets/           Repository ruleset definitions (main and v* tags)
├── migrations/              Alembic environment and revisions
├── src/example_app/         FastAPI application
├── tests/                   pytest suite, including a migration test
├── alembic.ini
├── Dockerfile
├── poetry.lock
├── poetry.toml
├── pyproject.toml
├── renovate.json
└── .pre-commit-config.yaml
```

## Quick start

```bash
pipx install poetry==2.5.1
poetry install

poetry run alembic upgrade head
poetry run uvicorn example_app.main:app --reload
```

`poetry.toml` sets `virtualenvs.in-project = true`, so Poetry creates `.venv` in the
repository. Prefix commands with `poetry run`, or activate the environment with
`poetry env activate`.

Open <http://127.0.0.1:8000/docs> for the OpenAPI UI. Useful endpoints:

```bash
curl http://127.0.0.1:8000/healthz
curl -X POST http://127.0.0.1:8000/items \
  -H 'content-type: application/json' \
  -d '{"name": "widget", "description": "a small widget"}'
curl http://127.0.0.1:8000/items
```

Settings come from `APP_*` environment variables (see `.env.example`). The default
database is `sqlite:///./app.db`.

## Tests, formatting and linting

```bash
poetry run pytest                 # unit tests and the Alembic migration test
poetry run black --check --diff . # formatting check
poetry run flake8 .               # lint
poetry run black .                # apply formatting
```

`make test`, `make lint` and `make format` wrap the same commands. The test suite
creates a temporary SQLite database per test, runs the application through
`TestClient`, and separately runs `alembic upgrade head` and `alembic downgrade base`
against another temporary SQLite database.

To add a model change:

```bash
poetry run alembic revision --autogenerate -m "add something"
poetry run alembic upgrade head
```

Add dependencies with Poetry, not by editing the lock file:

```bash
poetry add some-package
poetry add --group dev some-dev-package
poetry lock
```

Review autogenerated migrations before committing them. SQLite is used in tests, but
the application does not depend on SQLite for production.

## Pre-commit

Install the hooks once per clone:

```bash
poetry install
poetry run pre-commit install
```

`default_install_hook_types` in `.pre-commit-config.yaml` installs both hook types:

- **pre-commit**: whitespace and file hygiene, `black`, then `flake8`
- **pre-push**: `gitleaks` scans the commits being pushed for secrets

Run everything manually with:

```bash
poetry run pre-commit run --all-files
poetry run pre-commit run gitleaks --hook-stage pre-push --all-files
```

The hooks are a fast local check, not a security boundary. Anyone can use
`git commit --no-verify` or `git push --no-verify`, so CI runs black, flake8 and
gitleaks again on every pull request. The pre-push hook is there to catch a leaked
credential before it reaches GitHub, which is much cheaper than rotating it later.

## GitHub Actions

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `ci.yml` | push to `main`, every pull request | `black --check`, `flake8`, `pytest` on Python 3.14 |
| `security.yml` | push to `main`, every pull request, weekly | gitleaks over full history, Trivy filesystem scan, source SBOM artifact |
| `release.yml` | push to `main` | semantic-release bumps `pyproject.toml`, commits, tags, creates a GitHub release, then calls the container workflow |
| `container.yml` | called by `release.yml`, manual dispatch, pull requests that touch container inputs | builds the image, Trivy image scan, image SBOM, and pushes to ACR when a tag is supplied |

All workflows default to `contents: read`. Only the release job gets `contents: write`,
and only the container job gets `id-token: write` for Azure OIDC.

### CI

`lint` and `test` are separate jobs so a formatting failure and a test failure are
obvious in the pull request. Both install Poetry, run `poetry install` from
`poetry.lock`, and run the checks through `poetry run`. `actions/setup-python` caches
the Poetry virtualenv using `poetry.lock` as the cache key. The lint job also runs
`poetry check --lock`, so a stale lock file fails CI instead of silently resolving
different versions.

### Security

- **gitleaks** scans the full git history, not just the diff, because a secret removed
  in a later commit is still leaked.
- **Trivy filesystem** scans the repository and `poetry.lock` directly. Trivy
  understands Poetry's package groups and excludes development dependencies by
  default, so the scan reflects the runtime dependency set. `pyproject.toml` alone is
  not a lock file; the committed `poetry.lock` is what makes this repeatable.
- **Source SBOM** is generated by Syft from `poetry.lock` in CycloneDX JSON and
  uploaded as the `sbom-source.cyclonedx.json` workflow artifact.

High and critical vulnerabilities with an available fix fail both scans. Images and
packages with no upstream fix are ignored so the pipeline does not fail permanently on
an unfixable base image issue. Adjust `severity` and `ignore-unfixed` to match your
risk appetite.

### Release and automatic version bumps

The release workflow runs on every push to `main`, which in practice means every
merged pull request. Python Semantic Release reads conventional commit messages since
the last `v*` tag and decides the next version:

| Commit | Version effect |
| --- | --- |
| `fix: ...` or `perf: ...` | patch |
| `feat: ...` | minor |
| `feat!: ...` or `BREAKING CHANGE:` in the body | major |
| `chore:`, `docs:`, `ci:`, `test:`, `refactor:`, `build:`, `style:` | no release |

The scaffold commit is tagged `v0.1.0`. The project starts at `0.1.0` with
`allow_zero_version = true` and `major_on_zero = false`, so a breaking change before
1.0 bumps the minor version. Python Semantic Release uses the tag as its baseline: a
`feat:` merge produces `0.2.0` and a `fix:` merge produces `0.1.1`.

Push the tag with the branch when you first publish the repository:

```bash
git push -u origin main --follow-tags
```

Without a `v*` tag, semantic-release starts from `0.0.0` and could lower the version in
`pyproject.toml`. The release workflow fails with a clear error rather than allowing
that, so the initial tag must reach GitHub.

Python Semantic Release is in an optional Poetry group, so the release job installs
only what it needs with `poetry install --only release --no-root`.

When a release is due, the workflow:

1. writes the new version into `pyproject.toml`
2. updates `CHANGELOG.md`
3. commits as `chore(release): <version> [skip ci]`
4. creates the `v<version>` tag
5. creates the GitHub release
6. calls `container.yml` with the new tag and release commit SHA

The `[skip ci]` marker stops the version bump commit from starting another CI or
release run. The container build is called directly from the same workflow run, so it
does not depend on the tag push triggering a second workflow. Building the release
commit, rather than the original merge commit, means the version inside the image
matches the image tag.

Because merges are squashed, the pull request title becomes the commit subject. Use a
conventional pull request title (`feat: add widget filtering`, `fix: reject blank
names`) or semantic-release will not see a release-worthy change. A pull request title
checker is a reasonable addition if contributors forget.

### Container

`container.yml` builds with Buildx, loads the image into the local daemon, scans it
with Trivy, generates an SPDX SBOM, and only then pushes. If the scan fails, nothing is
pushed to the registry.

On a release tag such as `v0.2.0`, the pushed tags are:

- `v0.2.0`, the git tag
- `sha-<first 7 characters of the release commit>`
- `latest`, only for `v*` releases

On a pull request that changes the Dockerfile, `src/`, `migrations/`, `pyproject.toml`,
`poetry.lock`, `poetry.toml` or `alembic.ini`, the image is built and scanned but not
pushed. Manual dispatch with an empty tag does the same. This catches Dockerfile
breakage before release without giving pull requests registry credentials.

The builder installs the main dependency group with
`poetry install --only main` from `poetry.lock`, then the runtime copies the in-project
`.venv`. The image runs as a non-root user, listens on port 8000, stores SQLite data in
`/data`, and has a `HEALTHCHECK` that calls `/healthz`. It applies Debian security
updates at build time and does not ship pip or setuptools, which also removes pip's
vendored dependencies from the vulnerability scan.

```bash
docker build -t python-github-action-example:local .
docker run --rm -p 8000:8000 -v app-data:/data python-github-action-example:local

# Apply migrations in a one-off container
docker run --rm -v app-data:/data python-github-action-example:local alembic upgrade head
```

## Repository protection and rulesets

`main` must be changed only through pull requests. The ruleset in
`docs/rulesets/main.json` enforces:

- no branch deletion
- no force push (`non_fast_forward`)
- pull request required before merging
- squash merges only
- required status checks: `lint`, `test`, `gitleaks`, `trivy-fs`
- branches must be up to date with `main` before merging

`docs/rulesets/tags.json` protects `v*` tags from deletion, force moves and updates.

The only bypass actor is the release GitHub App described below. Humans, including
repository admins, do not get a bypass entry. Repository admins can still edit or
delete a ruleset, which is inherent to GitHub's permission model; the point is that
the normal path, including the admin's normal path, is a pull request.

`required_approving_review_count` is `0` so a solo maintainer can merge their own pull
request. Set it to `1` (or more) for a team.

### Applying the rulesets

Push the initial scaffold first, then apply the rulesets. Creating `main` through the
initial push is easier before direct pushes are blocked.

Create the release app first (next section), then substitute its numeric App ID:

```bash
OWNER=donbowman
REPO=python-github-action-example
APP_ID=123456   # the release GitHub App ID

jq --argjson id "$APP_ID" '.bypass_actors[0].actor_id = $id' \
  docs/rulesets/main.json \
  | gh api --method POST "repos/$OWNER/$REPO/rulesets" --input -

jq --argjson id "$APP_ID" '.bypass_actors[0].actor_id = $id' \
  docs/rulesets/tags.json \
  | gh api --method POST "repos/$OWNER/$REPO/rulesets" --input -
```

Check them with:

```bash
gh api "repos/$OWNER/$REPO/rulesets" --jq '.[] | {name, target, enforcement}'
```

The JSON files are templates. `actor_id: 0` is not a valid app ID; replace it with the
real App ID using the `jq` command above or add the app through
**Settings > Rules > Rulesets > Protect main > Bypass list**.

## The release GitHub App, without a PAT

The release workflow must commit and tag on a protected `main`. The built-in
`GITHUB_TOKEN` cannot bypass a ruleset, and pushes made with it do not trigger other
workflows. A fine-grained personal access token would work, but it is a long-lived
credential tied to a person. Use a GitHub App installation token instead.

1. Create a GitHub App under **Settings > Developer settings > GitHub Apps > New
   GitHub App**.
2. Set the homepage to this repository. Disable the webhook; it is not needed.
3. Repository permissions: **Contents: Read and write**, **Metadata: Read-only**.
   Nothing else.
4. Install the app on this repository only.
5. Generate a private key and note the **App ID**.

Configure the repository:

```bash
gh variable set RELEASE_APP_ID --body "<app id>"
gh secret set RELEASE_APP_PRIVATE_KEY < /path/to/app-private-key.pem
```

The workflow uses `actions/create-github-app-token@v3` with those values. The token is
scoped to this repository, has only `contents: write`, and expires after one hour.
`semantic-release` uses it for the push, tag and release. The app is the ruleset bypass
actor, so the push succeeds without weakening protection for people.

If the release job gets a 403 or "protected branch" error, check in this order: the app
is installed on the repository, `RELEASE_APP_ID` and
`RELEASE_APP_PRIVATE_KEY` are set, the app has Contents write, and the app is in the
ruleset bypass list.

## Azure Container Registry with GitHub OIDC, without a PAT

The container workflow authenticates to Azure with a federated credential. There is no
client secret, no registry password and no personal access token in GitHub. The trust
relationship is between this repository's GitHub OIDC identity and an Entra ID app
registration.

### Create the registry and identity

```bash
RG=rg-python-gha-example
ACR=acrpythonghaexample     # must be globally unique, lowercase alphanumeric
LOCATION=canadacentral

az group create --name "$RG" --location "$LOCATION"
az acr create --resource-group "$RG" --name "$ACR" \
  --sku Basic --admin-enabled false

APP_NAME=github-python-github-action-example
APP_ID=$(az ad app create --display-name "$APP_NAME" --query appId -o tsv)
SP_ID=$(az ad sp create --id "$APP_ID" --query id -o tsv)

# Trust only pushes from main in this repository.
az ad app federated-credential create --id "$APP_ID" --parameters '{
  "name": "github-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:donbowman/python-github-action-example:ref:refs/heads/main",
  "audiences": ["api://AzureADTokenExchange"]
}'

# Push permission on this registry only.
ACR_ID=$(az acr show --name "$ACR" --query id -o tsv)
az role assignment create --assignee "$SP_ID" --role AcrPush --scope "$ACR_ID"
```

`AcrPush` includes pull and push. The registry admin account stays disabled, so there
is no registry username or password to leak.

The federated credential subject is exact. If the repository is renamed, transferred
or forked, update the subject. If you later put the job behind a GitHub environment,
the subject changes to `repo:OWNER/REPO:environment:NAME` and the credential must be
updated to match.

### Set repository variables

```bash
TENANT_ID=$(az account show --query tenantId -o tsv)
SUBSCRIPTION_ID=$(az account show --query id -o tsv)
LOGIN_SERVER=$(az acr show --name "$ACR" --query loginServer -o tsv)

gh variable set AZURE_CLIENT_ID --body "$APP_ID"
gh variable set AZURE_TENANT_ID --body "$TENANT_ID"
gh variable set AZURE_SUBSCRIPTION_ID --body "$SUBSCRIPTION_ID"
gh variable set ACR_NAME --body "$ACR"
gh variable set ACR_LOGIN_SERVER --body "$LOGIN_SERVER"
```

At push time the workflow:

1. requests a GitHub OIDC token (`id-token: write`)
2. exchanges it with Entra ID through `azure/login@v3`
3. obtains an ACR token with `az acr login --expose-token`
4. logs Docker in with that short-lived token as the password
5. pushes `v<version>`, `sha-<short>` and, for releases, `latest`

Images are named
`<login-server>/python-github-action-example:<tag>`, for example
`acrpythonghaexample.azurecr.io/python-github-action-example:v0.2.0`.

### Why not GHCR?

GitHub Container Registry (`ghcr.io`) is a perfectly good registry, and it is simpler
to bootstrap: `GITHUB_TOKEN` with `packages: write` can push, so there is no Azure
setup at all. That is the right choice for a purely GitHub-hosted project.

The trade-off is future Azure Kubernetes Service work. ACR is a first-class Azure
resource: AKS can pull with its kubelet or workload managed identity through
`AcrPull`, with no image pull secret; the registry participates in Azure RBAC, private
endpoints, geo-replication, retention policies and Microsoft Defender for Cloud. GHCR
works with AKS too, but you end up managing pull secrets or extra workload identity
federation for a non-Azure registry. This example chooses ACR to keep that path short.
If you do not need AKS, switching the container workflow to GHCR removes the whole
Azure section above.

## Dependency updates

Renovate is configured in `renovate.json`. Install the Renovate GitHub App on the
repository to enable it. Renovate keeps `pyproject.toml` and `poetry.lock`, the
Dockerfile base image, the pre-commit hook revisions and the GitHub Actions versions
current, groups related updates, and uses conventional commit messages so dependency
pull requests flow through semantic-release correctly. Lock file maintenance and the
dependency dashboard are enabled.

Dependabot is the built-in alternative and needs no app install. If you prefer it,
delete `renovate.json` and add `.github/dependabot.yml`:

```yaml
version: 2
updates:
  - package-ecosystem: pip
    directory: "/"
    schedule:
      interval: weekly
  - package-ecosystem: github-actions
    directory: "/"
    schedule:
      interval: weekly
  - package-ecosystem: docker
    directory: "/"
    schedule:
      interval: weekly
```

Dependabot's `pip` ecosystem understands `poetry.lock`, so no separate Poetry
ecosystem is needed. Do not run both Renovate and Dependabot at once unless duplicate
pull requests are acceptable.

## Setup checklist

1. Push this repository to GitHub, including the initial `v0.1.0` tag:
   `git push -u origin main --follow-tags`. This creates `main` before rulesets exist.
2. Create the release GitHub App, install it on this repository, and set
   `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY`. The release job is skipped until
   `RELEASE_APP_ID` exists, so the initial push does not fail on a missing app.
3. Make sure **Settings > Actions > General** allows GitHub Actions to run.
4. Create the Azure resource group, registry, app registration, federated credential
   and `AcrPush` role assignment. Set the five Azure/ACR variables.
5. Apply both rulesets with the release App ID in `bypass_actors`.
6. Install the Renovate app, or switch to Dependabot.
7. Open a pull request with a release-worthy conventional title and merge it. The
   release workflow should create a tag, a GitHub release and a container image.

## Troubleshooting

- **`poetry.lock` is out of date**: run `poetry lock`, then commit both
  `pyproject.toml` and `poetry.lock`. CI runs `poetry check --lock`.
- **`poetry: command not found`**: install Poetry 2.5.1 with
  `pipx install poetry==2.5.1`, or use the official installer.
- **Docker build cannot find `poetry.lock`**: make sure it is committed. It must be in
  the build context; `.dockerignore` does not exclude it.
- **Release reports no release**: there is no `feat`, `fix`, `perf` or breaking change
  since the last tag, or the squash merge title is not conventional.
- **Release push rejected**: the App is not a ruleset bypass actor, is not installed on
  the repository, or lacks Contents write.
- **`AADSTS700213` or no matching federated identity**: the OIDC subject does not
  match. Check the branch name, repository owner and repository name in the federated
  credential.
- **ACR push denied**: the service principal lacks `AcrPush` on the registry scope, or
  `ACR_LOGIN_SERVER` does not match the registry. Role assignments can take a few
  minutes to propagate.
- **Trivy fails on a base image**: inspect the table output. If there is no upstream
  fix, `ignore-unfixed` should already suppress it; otherwise update the base image or
  add a narrowly scoped ignore with a review date.
- **Container PR job did not run**: the path filter only includes container inputs.
  This job is not a required check for that reason.

For stronger supply chain hardening, pin third-party actions to full commit SHAs.
Renovate can manage the pins. `uses: owner/action@v7` is readable and receives
security updates automatically, but a tag can move; a SHA cannot.
